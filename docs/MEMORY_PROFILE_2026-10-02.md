# 游戏运行内存实测（2026-10-02）

此文保留优化前的初次测量。后续源码优化、相同场景的前后对照和剩余限制见 [游戏内存优化与对照验证](MEMORY_OPTIMIZATION_2026-10-02.md)。

当前生产构建的页面进程内存偏高。新生涯连续游玩时采样峰值约 665 MiB，已完成 5 个赛季的生涯两次运行峰值约 865–876 MiB。操作结束后会回落；本轮没有发现明显的逐次切页 JS/DOM 泄漏。

## 测量范围与口径

- 从当前工作区构建生产版，未使用 Vite 开发模式，未覆盖 `h5/` 或发布 ZIP。
- macOS、Chromium 151.0.7922.34，393×852 视口、DPR 3。移动视口不等于手机真机。
- 独立浏览器、独立浏览器上下文、固定 Seed `memory-audit-2026-10-02`，使用当前 bundled NBA 数据完成扩军、选秀、自由市场和开幕阵容流程。没有读取或覆盖玩家存档。
- 每 250 ms 获取主线程 JS 堆和浏览器进程 RSS；表中页面 RSS 取唯一活动页面的 renderer 进程，排除约 45 MiB 的空闲备用 renderer。该进程包含页面与两个后台 Worker。
- RSS 包含浏览器运行时、已提交堆、代码和图片等，不等于游戏业务对象大小；GPU 进程另计。浏览器进程树 RSS 之和会重复计算共享页，不能当作纯游戏内存。
- 阶段快照会强制主线程 GC，用于比较存活对象；未在正常游玩期间强制 Worker GC。250 ms 采样可能漏掉更短的峰值。
- 构建 JS SHA-256：`520db2cb27a0240c8c2e5a38880d752dd45e1030729962a452ba55202bf48735`。

## 实测结果

| 场景 | 主线程 GC 后 JS 堆 | 页面 RSS | 说明 |
|---|---:|---:|---|
| 空白页 | 0.57 MiB | 约 64 MiB | 浏览器基础开销对照 |
| 游戏首页 | 4.78 MiB | 约 155 MiB | bundled 数据已初始化 |
| 新生涯进入常规赛 | 9.12 MiB | 324.24 MiB | 649 名球员，0 个历史赛季 |
| 新生涯切页第 10 轮 | 11.40 MiB | 324.25 MiB | 回到相同赛季主页采样 |
| 新生涯切页第 50 轮 | 11.75 MiB | 403.48 MiB | 650 次导航，包含头像/列表页面 |
| 新生涯完成 20 场比赛、5 次手动存档并静置 5 秒 | 12.15 MiB | 494.80 MiB | 自动存档也正常完成 |
| 5 个赛季后进入常规赛 | 10.81 MiB | 413.29 MiB | 1,225 名球员，5 个历史赛季 |
| 5 个赛季后完成 5 场比赛、1 次手动存档并静置 5 秒 | 18.76 MiB | 644.45 MiB | 首次运行 |

| 采样峰值 | 新生涯 | 5 个赛季生涯 |
|---|---:|---:|
| 页面 RSS | 664.62 MiB | 864.75 MiB |
| 主线程未强制回收的 JS 堆 | 45.38 MiB | 85.66 MiB |

最高页面 RSS 出现在手动保存阶段。5 赛季测试中，比赛模拟/自动保存阶段峰值为 770.63 MiB，手动保存阶段峰值为 864.75 MiB。截图与状态确认新生涯实际打了 20 场（8 胜 12 负），5 赛季生涯实际打了 5 场（5 胜 0 负）。两个完成的浏览器场景均无页面错误。

切页第 10–50 轮主线程 JS 堆只增加 0.35 MiB；每轮回到相同页面时，DOM nodes 均为 702，事件监听器均为 296。页面 RSS 的额外增长不能直接判定为 JS 泄漏，仍可能涉及原生资源缓存和运行时保留。存档抽屉关闭后监听器变为 449，并在随后重复保存中保持稳定。

## 代码对应的增长与峰值来源

- `src/app/simulationWorkerClient.ts:79` 向后台线程发送整份状态；`src/app/simulation.worker.ts:9` 再返回整份结果。跨线程会复制状态，主线程旧状态还会短暂保留。模拟 Worker 空闲 5 分钟关闭；存档 Worker 正常路径常驻。
- `src/storage/SaveService.ts:375` 保存期间读出上一版本，再序列化新版本并写入暂存、备份和主存档；`src/storage/SaveCodec.worker.ts` 同时处理哈希序列化和 JSON；gzip/base64 又产生临时缓冲。大存档会放大这些峰值。
- `src/game/history/HistoryCompressionService.ts` 仅最近 1 个历史赛季保留完整常规赛详情，但每个旧赛季的联盟轻量比分、重大比赛和用户季后赛仍保留。
- 退役球员仍留在 `players`，每年还会增加新球员。实际测试存档未压缩 JSON 从 1.42 MiB 增到 4.93 MiB；这是磁盘数据大小，不能直接当 RAM。
- 26 条 NBA 头像 strip 的全部 RGBA 解码约 15.87 MiB，GPU/浏览器缓存另有开销；退役头像首次加载后约 1.76 MiB 的 base64 数据常驻。它们有成本，但不能单独解释约 865 MiB 的页面峰值。

## 闲置释放补测

另起一个相同的 5 赛季场景，完成切页、5 场比赛和一次手动保存，再等待模拟 Worker 的 5 分钟自动关闭。第二次采样页面 RSS 峰值 875.68 MiB，主线程 JS 峰值 88.66 MiB。

| 阶段 | 页面 RSS | 后台 Worker 数 |
|---|---:|---:|
| 保存后静置 5 秒 | 518.34 MiB | 2 |
| 再闲置 45 秒 | 403.13 MiB | 2 |
| 再闲置 270 秒 | 403.14 MiB | 2 |
| 再闲置 315 秒 | 391.13 MiB | 1 |

主线程 GC 后 JS 堆保持 18.75 MiB。存档 Worker 的存活 JS 堆从闲置前的 47.28 MiB 自动回收到 0.44 MiB，分配堆从 93.06 MiB 回收到 1.25 MiB；模拟 Worker 已退出。最后单独强制剩余 Worker GC，其 JS 堆和页面 RSS 都没有继续下降。

因此，保存峰值有大量临时内存能够自行回收，模拟 Worker 的空闲关闭机制也有效；但关闭模拟线程只额外降低约 12 MiB，单纯加速线程关闭不足以解决数百 MiB 的页面占用。剩余 RSS 不能全部归因于存活 JS 对象，本轮未做原生分配栈、GPU 纹理或浏览器进程 footprint 分解。

## 建议与边界

优先降低存档时的完整状态/字符串复制，并处理长生涯历史、退役球员的存储结构。后台线程空闲释放可作补充优化，但本轮证据显示收益较小。当前不能把主线程十几 MiB 的 JS 堆作为“游戏很省内存”的依据。

本轮只测试和记录证据，未修改游戏业务逻辑、依赖或发布包。尚未测量 iOS/Android 虎扑 WebView 真机、超过 5 个完整赛季的生涯、三个大存档并存、海报生成和跨年度切换时的峰值；本次结果不能据此保证手机不会因内存压力被系统回收。
